## Design choices

- **Real queries, honest labels.** ESCI gives real shopper queries with human relevance labels (E/S/C/I) but no prices,
  stock, categories or vendors. Those are generated from a fixed seed and called synthetic everywhere they appear
  (catalog report, protocol, this note); the relevance labels are never changed.
- **Method fixed before results** (ADR-013). The protocol was approved and tagged (`protocol-v1`) before any search was
  measured; the one later change (v1.1, hidden products) was approved and tagged before any lost-demand result. Tuning
  only on the 300 dev queries; the 700 test queries are read once, in M8. The baseline script refuses test queries
  and test-judged products.
- **Hidden products** (v1.1, D12). All Exact products of 20 % of each set's queries are left out of the shop
  (hidden-test: 140 queries, 1,081 products, 5.4 % of the catalog; hidden-dev: 60 queries, 508 products): known
  missing demand that the M6 lost-demand job must find.
- **Import through Odoo's API, not SQL** (ADR-019). JSON-2 as the integration user, so Odoo's own rules run (access
  rights, computed fields, stock moves). Idempotent: lookups by internal reference, only differing fields written; a
  second full run changes nothing. Stock comes from real inventory adjustments, so every unit has a stock move.
- **A simple, realistic shop.** Cost = vendor price, no sales tax, availability shown, out-of-stock products findable
  but not orderable (1,828 at 0 to start).
- **Reproducible bytes.** Seeded streams (`SHA-256(seed:label)`), sorted outputs and a manifest of hashes: two
  builds give identical files, checked on every slice change.

## Results

- **Catalog**: 19,869 products imported in 442 s (21.9 ms per product); 18,041 in stock, 1,828 at 0; second run
  40 s, nothing changed (`results/summary/catalog-import.md`).
- **Baseline** (`results/summary/baseline-search.md`, `docs/report/notes/baseline-search.md`): Odoo's own search shows
  no result for **73 of 300 dev queries (24 %)** although every wanted product is in the shop — 15 % for 1–2 words,
  23 % for 3–4, 33 % for 5+, 46 % with a negation word. 17 of the 20 hand-picked queries fail while their controls
  succeed. Cause: every word must appear in the product text; no word forms, synonyms, brand field or ranking.

## Problems met (and what fixed them)

| Problem | Cause | Fix |
|---|---|---|
| Slice build peaked at 1.57 GiB | pyarrow pre-buffers a whole row group; ESCI files have one | `pre_buffer=False` + 8 MiB buffered stream: 639 MiB, same output hashes |
| 7 of 200 products rewritten on every import | Odoo's HTML sanitizer stores `'` and `"` unescaped | quotes not escaped; HTML compared by its decoded text |
| Writing stock again created empty moves | `action_apply_inventory` moves even an unchanged quantity | only products whose quantity differs are adjusted |
| Updating 19,869 products one call each was slow | one `write` per product | identical changes grouped into one `write`: 122 s |
| A `--no-dev` run replaced the committed baseline table | the table was written by every run | a partial run writes its run folder only (2.6) |
| `python3` hung in Git Bash | the Windows Store stub | always `uv run python` |
| `import verify` failed after a partial import | it sampled from all 19,869 products | `--limit N`, as the import (2.6) |
| Cluster health yellow on a fresh stack | Kibana 9.5 creates `.entity_analytics.watchlists.default` with one replica | not blocking; follow-up: set its replicas to 0 in `es-setup` |
| Free disk 72 GB → 37 GB (2026-11-19) | other projects' images and containers | enough for M3; nothing pruned |
