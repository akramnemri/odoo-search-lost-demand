## 3. Catalog slice and query sets

Goal: a catalog of ~20,000 products (spec) in which **every judged product of every evaluation query exists**, so NDCG is fair.

Proposed construction (default; approved in Task 2.2):

1. Keep `product_locale = us` and `small_version = 1` (queries with the most complete judgments).
2. Sample with a fixed seed:
   - **dev set**: 300 queries from the ESCI *train* split — used for all relevance tuning;
   - **test set**: 700 queries from the ESCI *test* split — used once, for final reporting.
3. **Catalog** = union of all products judged (any label) for the dev + test queries (≈ 20–23k products; record the exact count).
4. **Traffic pool** (virtual shoppers) = dev + test queries. This does not leak labels into NDCG **as long as no click-based
   ranking feature is used**. If a popularity feature is ever used, NDCG runs must disable it or exclude test-query traffic (ADR).
5. **qrels** file: query ID, product ID, label, gain.
6. **Hidden set** (detection test): 20 % of the catalog size, chosen with a fixed seed, stratified by category,
   **only among products that are the Exact (E) match of at least one traffic query** (otherwise no shopper would ever look
   for them and detection would be impossible by construction).
7. **Out-of-stock set**: 10 % of the remaining products start with zero stock (default), for FR3 and the out-of-stock signal.

Tests: same seed → identical output hashes; dev ∩ test = ∅; every judged product of every selected query is in the catalog;
every hidden product is an E-target of a traffic query.

## 4. Synthetic enrichment (labelled synthetic everywhere)

ESCI products have no category, price, stock or vendor. We add them deterministically, with a seed and documented rules:

| Field | Rule (default) |
|---|---|
| Category | Keyword rules on title + bullet points mapping to ~15–20 top-level public categories (config file `tools/shoptools/data/categories.toml`), "Other" as fallback. Report coverage (% not "Other") |
| Price | Per-category log-normal distribution, bounded, rounded to `.99`; seeded |
| Stock | Seeded quantity distribution; the out-of-stock set (§3) gets 0 |
| Vendor | ~20 synthetic vendors; vendor chosen from a hash of the brand (same brand → same vendor) |
| Vendor price / min qty / lead time | 55–75 % of list price; min qty 1–10; lead time 2–14 days |
| Description | ESCI description + bullet points, HTML stripped, length-capped |
| Reference | ESCI `product_id` stored as the Odoo internal reference (`default_code`) |

The slice builder writes an enrichment report (aggregates only: distributions per category, coverage) to
`results/summary/enrichment-report.md`.

**Odoo import mapping:** ESCI title → name; description → website/sales description; brand → `brand` (module field);
color → kept for indexing (attribute only if needed); category → public category (+ a simple internal category);
price → list price; vendor → partner + vendor pricelist line; stock → on-hand quantity via a proper inventory adjustment;
all products published at import (the hidden set is applied only during the detection campaign).
The importer writes `data/processed/odoo_id_map.parquet` (ESCI product ID ↔ Odoo template ID) for Locust and evaluation.

## 6. Query design

| Engine | Definition |
|---|---|
| `odoo` | Odoo's native shop search (what shops have today) |
| `es_plain` | `multi_match` with default parameters over `name.std`, `description.std`, `brand.std`; no fuzziness, synonyms, boosts or stock rule |
| `es_tuned` | The configuration chosen on the dev set (relevance only) |
| `es_tuned_stock` | `es_tuned` + the in-stock rule (FR3) — the production default |
| `hybrid` (FR13) | `es_tuned_stock` fused with kNN on embeddings, fusion done in the module |

All engines apply the same filters: `published = true`, current website, plus FR5 filters.

**Tuning space** (dev set only, one change per experiment, each recorded in `docs/evaluation/experiments.md`
with its NDCG@10 and run ID): analyzers and stemmer, field boosts, `best_fields` vs `cross_fields` vs `most_fields`,
fuzziness (`AUTO`, `prefix_length`), phrase boost on name, brand exact-match boost, `minimum_should_match`, synonyms seed.
Known interactions to check: fuzziness is not applied to synonym-expanded tokens, and `cross_fields` does not support fuzziness.

**In-stock rule (FR3).** Two implementations, both measured on the dev set:
(a) tiered — sort by `in_stock` desc, then score (literal reading of FR3); (b) boosted — strong `should` boost on `in_stock`.
Default (a) unless the supervisor accepts (b). Report the NDCG cost of the stock rule (`es_tuned` vs `es_tuned_stock`):
ESCI labels ignore stock, so some loss is expected and is a product trade-off, not a bug.

**Filters and facets (FR5).** Filters in `bool.filter`; facet counts with aggregations (categories, `brand.kw`, price ranges,
in-stock) and `post_filter`, so each facet's counts ignore its own selection.

**Autocomplete (FR4).** Server-side override of the website's existing autocomplete route so the standard search bar keeps working:
(1) popular queries that returned results (aggregated from events into a small suggestions index, refreshed by a job),
(2) product names via `bool_prefix` on `name.sayt`. Budget: < 100 ms; on timeout fall back to Odoo's suggestions.

**Semantic search (FR13).** A small open model run on CPU in the `embedder` service (choose in a spike; e.g. a MiniLM-class
sentence-transformers model; verify license and latency). Product embeddings computed offline in batches; query embedding
at search time with a 150 ms timeout and fallback to keyword. Fusion in the module: client-side RRF (`1/(k+rank)`, k≈60)
or normalized linear combination, tuned on the dev set. The `rrf` and `linear` retrievers are Enterprise-only: do not use them.

## 8. Lost-demand definitions

### 8.1 Query normalization (in the module, at event creation)

Unicode NFKC, case-fold, trim, collapse whitespace, strip surrounding punctuation; no stemming (keep it readable for the buyer);
PII masks (`<email>`, `<phone>`) stay in place. Unit-tested with examples.

### 8.2 Signals (defaults; all thresholds are module settings)

Events considered: `source = shop`, `traffic ∈ {human, virtual}`, inside window **W = 7 days** (default; the detection
campaign uses a window covering its run).

| Signal | Definition (default) |
|---|---|
| Zero-result query | `count(search, result_count = 0, query_normalized = q) ≥ 3` **and** distinct sessions ≥ 2 |
| Unsatisfied query (needs approval) | Searches with results but no click/add-to-cart carrying the same `search.id` within 120 s: count ≥ 5, unsatisfied rate ≥ 0.6, distinct sessions ≥ 2 |
| Out-of-stock demand | Per product: `score = 1·views + 2·clicks + 5·add_to_cart` ≥ 10 with distinct sessions ≥ 2, **and** current Odoo stock ≤ 0 |

Implementation notes: aggregations (`terms`/`composite` with `cardinality` sub-aggregations); for the unsatisfied signal,
compute search IDs with and without follow-up interaction in Python from composite aggregations, or use a continuous
transform if it is available on Basic (verify). Trend = count in W vs count in the previous W
(`up` > +20 %, `down` < −20 %, else `flat`).

### 8.3 Suggested restock quantity (heuristic, not a forecast)

`qty = max(vendor_min_qty, ceil(add_to_cart_in_W × horizon_days / W_days))`, horizon 14 days (default).
Documented as a heuristic in the UI tooltip and in the report.

## 9. Shopper model (Locust, FR11)

Documented, configurable (`loadtest/shopper_model.toml`), seeded. It is a simulation: report it as a threat to validity.

| Behavior | Default |
|---|---|
| Query choice | From the traffic pool with Zipf-like popularity (s ≈ 1.1), so queries repeat as in real shops |
| Typos | With probability 0.15, one edit (swap, delete, duplicate, keyboard-neighbor replace) in one word of ≥ 4 letters |
| Zero results | Leave (0.7) or try another query (0.3) |
| Click | `P = attractiveness(label) × 1/log2(position + 1)`; attractiveness E 0.6, S 0.25, C 0.1, I 0.03, unjudged 0.03; at most 2 clicks per search |
| Add to cart after click | E 0.35, S 0.15, C 0.10, otherwise 0.02 (only if purchasable) |
| Checkout | 0.4 of sessions with a non-empty cart, using the demo payment provider |
| Think time | 2–8 s |

Labels come from the qrels via the id map (ESCI ID ↔ Odoo template ID).

## 11. Evaluation protocol (spec section 11)

Every campaign: restore the baseline snapshot, record `run.json`, keep raw outputs in `results/<run-id>/`,
write the summary to `results/summary/`, and report in `docs/evaluation/results.md`.

### 11.1 Search quality — NDCG@10 (target: tuned search scores highest of the three)

- Gains: E = 1.0, S = 0.1, C = 0.01, I = 0 (the ESCI benchmark convention; verify in the ESCI repository).
- `DCG@10 = Σ gain_i / log2(i + 1)` over the first 10 results; `IDCG@10` from the ideal ordering of the query's judged products;
  unjudged results count as gain 0. Report also "judged@10" (share of top-10 results that are judged).
- Harness: `uv run shop eval ndcg --set dev|test --engine <list> --mode http|direct`.
  `http` goes through the real `/shop` page with the guarded engine switch (what shoppers see; used for reported numbers);
  `direct` queries Elasticsearch only (fast tuning loop). A consistency check compares both modes on the dev set.
- Engines reported: `odoo`, `es_plain`, `es_tuned` (+ `es_tuned_stock` and `hybrid` as extra rows).
- Statistics: mean NDCG@10 with a 95 % bootstrap confidence interval (10,000 resamples, seeded); paired randomization
  test between engines on per-query scores; report differences and p-values.
- The test set is run **once**, after the configuration freeze (Task 8.1).
- Threats: labels reflect Amazon's catalog; our catalog is a slice; Odoo's native ordering is not relevance-based by design.

### 11.2 Lost-demand detection — hidden catalog (target: ≥ 80 % of hidden products flagged)

1. Restore baseline; `uv run shop eval hide --apply` unpublishes the hidden set; index updated.
2. Run the Locust `detection` profile (default: 50 users, 45 min, traffic pool, Zipf) with a run ID.
3. Run the lost-demand job with a window covering the run; export the report.
4. A hidden product **p is detected** if at least one query q with label(q, p) = E appears in the report
   (zero-result or, if approved, unsatisfied list). Only hidden products searched at least 3 times during the run count.
5. Compute recall (target ≥ 0.8) and precision (share of reported queries that target a hidden or out-of-stock product);
   list misses with reasons.
6. `uv run shop eval hide --revert`.

Secondary metric: recall of the out-of-stock signal on the out-of-stock set.

### 11.3 Speed (targets: page p95 < 1 s; Elasticsearch query p95 < 100 ms)

Baseline restored; Odoo workers set for load tests (`01` §5.3); 2-minute warm-up; Locust `speed` profile: 50 users,
spawn rate 5/s, 10 minutes, search-heavy mix; three repetitions. Metrics: search-page p50/p95/p99 and failure rate (Locust),
`took_ms` p95 from the run's search events. Record the machine profile, RAM profile and settings.

### 11.4 Freshness (targets: event < 10 s; product change < 60 s)

- Events: 200 probe searches with unique tokens (`traffic = probe`); poll Elasticsearch every 200 ms until each event is
  searchable; delay = found time − `@timestamp` (same host clock). Report p50/p95/max. "Visible in Kibana" = searchable
  delay + dashboard refresh interval (5 s): report both.
- Products (FR1): 30 stock or price changes through the Odoo API; poll shop search until the change shows. Report p50/p95/max.

### 11.5 Volume (targets: ≥ 10 million events; dashboards load in < 5 s)

Replay REES46 (e.g. the first two weeks of October 2019 at high speed) until `source: rees46` holds ≥ 10M events.
Record ingest throughput, store size, heap usage. Load the Volume and Demand-by-category dashboards 5 times over 30 days of data:
time until all panels have rendered (automated with a headless browser waiting for Kibana's render-complete markers if feasible — verify —
otherwise a stopwatch on a screen recording; state the method).

### 11.6 Usefulness (target: feedback included in the report)

Interview a real shop owner before (Milestone 1) and after a demo (Milestone 11), with the guide in `docs/pilot/`,
consent, anonymised notes; summarize what they would use, change or not trust.
